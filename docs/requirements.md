# Требования к Ticketeer

Этот документ фиксирует согласованные функциональные и технические требования к Ticketeer. Перечисленные возможности описывают требуемое поведение системы и не означают, что оно уже реализовано.

## Согласованные требования

### Пользователи и авторизация

- В системе предусмотрены две роли: кассир и администратор.
- Самостоятельная регистрация отсутствует.
- Учётные записи создаёт администратор.
- Авторизация осуществляется по логину и паролю.
- Пользователи принадлежат группам (участкам).
- Администратор может создавать и удалять группы, создавать и удалять пользователей, добавлять пользователей в группы, исключать их из групп и переводить между группами.
- Административные функции доступны только администратору.

### Вопросы и темы

- Вопросы распределяются по тематическим разделам.
- Каждый вопрос содержит текст и несколько вариантов ответа.
- У каждого вопроса ровно один правильный ответ.
- Администратор может создавать и редактировать вопросы, варианты ответов и темы.
- Вопросы могут использоваться в разных билетах и экзаменах.

### Проверка ответов

- После выбора правильного ответа выбранный вариант подсвечивается зелёным.
- После выбора неправильного ответа выбранный вариант подсвечивается красным, а правильный — зелёным.
- После ответа изменить выбор нельзя.
- Пользователь может перейти к следующему вопросу.
- Ответы учитываются при подсчёте результатов.

### Тренировочные билеты

Предусмотрены два способа формирования билетов:

1. Ручной — администратор составляет билет из существующих вопросов.
2. Автоматический — система случайным образом выбирает вопросы из указанной темы.

Правила прохождения:

- ограничение времени отсутствует;
- ограничение количества ошибок отсутствует;
- результаты сохраняются;
- прогресс по готовым билетам учитывается отдельно от случайных тренировок.

### Экзамены

Предусмотрены два способа формирования экзаменов:

1. Ручной — администратор выбирает вопросы и создаёт экзаменационный вариант.
2. Автоматический — система случайным образом формирует вариант из существующих вопросов.

Правила экзамена:

- экзамен состоит из 10 вопросов;
- на прохождение отводится 20 минут;
- допускается не более 2 ошибок;
- при третьей ошибке экзамен досрочно завершается с результатом «Не сдан»;
- при истечении времени незавершённый экзамен считается несданным;
- для успешной сдачи необходимо ответить на все 10 вопросов, допустив не более 2 ошибок;
- результат каждой попытки сохраняется;
- повторное прохождение допускается;
- механизм разрешения повторного прохождения проверяющим на текущем этапе не предусматривается.

### Профиль и статистика

Кассир может просматривать:

- информацию о своём аккаунте и группе;
- процент правильных ответов;
- количество пройденных билетов относительно общего количества;
- историю прохождений;
- график активности: частоту входов и прохождений по дням.

Администратор может просматривать:

- статистику каждого пользователя;
- сравнительную таблицу пользователей;
- результаты сотрудников с учётом их групп.

### Пользовательский интерфейс

Необходимо предусмотреть:

- страницу авторизации;
- главную страницу с тематическими разделами и экзаменами;
- верхнее навигационное меню;
- поисковую строку для поиска вопросов и билетов;
- страницы прохождения билетов и экзаменов;
- страницу результатов;
- профиль пользователя со статистикой;
- административную панель.

### Технологический стек

Frontend:

- Vue 3;
- TypeScript;
- Vite;
- Vue Router;
- Pinia;
- UnoCSS.

Backend:

- C#;
- ASP.NET Core;
- .NET 10;
- REST API.

База данных:

- PostgreSQL.

## Пока не реализованные возможности

По состоянию репозитория на момент подготовки документа прикладная функциональность находится в плане разработки. В частности, пока не реализованы:

- авторизация, роли, пользователи и группы;
- управление темами, вопросами и вариантами ответов;
- ручное и автоматическое формирование тренировочных билетов;
- прохождение билетов и проверка ответов;
- ручное и автоматическое формирование экзаменов;
- ограничения экзамена по времени и количеству ошибок;
- сохранение результатов и повторные попытки;
- профиль, история, пользовательская и групповая статистика;
- поиск вопросов и билетов;
- административная панель и остальные прикладные страницы;
- REST API и доменная модель backend;
- интеграция приложения с PostgreSQL;
- подключение UnoCSS к frontend.

Наличие каркасов проектов и отдельных зависимостей не считается реализацией перечисленных возможностей.

## Вопросы для дальнейшего проектирования

До реализации необходимо отдельно определить:

- правила количества и распределения вопросов при автоматическом формировании тренировочного билета;
- критерии случайного отбора вопросов для автоматического экзамена и допустимость повторов между попытками;
- жизненный цикл тем, вопросов, групп и пользователей при удалении, включая сохранение исторических результатов;
- точные формулы показателей статистики и границы периода для графика активности;
- критерии, по которым готовый билет считается пройденным, и способ расчёта общего количества билетов;
- поля и режим работы поиска по вопросам и билетам;
- требования к безопасности сессий, срокам действия авторизации и восстановлению доступа;
- будущие правила, по которым проверяющий сможет разрешать или запрещать повторное прохождение экзамена.
